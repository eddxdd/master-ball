# Roadmap

Phased so that each phase ships something demoable, building on a solid, working foundation. Don't start a later phase's tooling before the current phase's core loop actually works end-to-end — a small working thing beats a half-built ambitious thing.

> **Scope note:** phases below reflect the narrowed product scope in [`product-research.md`](./product-research.md) — the two flagship v1 features are the **Conversational Team Doctor** (Phase 2) and the **Mental-Game Coach** (Phase 3), not "clone every feature of every existing tool." The AI video/battle-postmortem feature (analyzing a user-uploaded recording of a Pokémon Champions match, since that game has no replay export) is explicitly a **Premium/stretch feature** in Phase 7, not core scope — it's the most differentiated idea from the research but also the most expensive to build well.
>
> **Tools vs. AI note:** Phase 1 (the Pokédex, Team Builder, and Calculator) is scoped as a first-class deliverable in its own right, not a placeholder to rush past — Phases 2–3 (the AI coaching layer) are what get layered on top of it, and they're only a real differentiator if the tools underneath them are genuinely excellent. See [`README.md`](./README.md#core-product-pillars) for the full pillar breakdown.
>
> **Platform note:** the whole build targets a single website, shipped as an installable PWA — there is no committed native/Google Play app anywhere in Phases 0–6. Native packaging (Capacitor) is explicitly optional and lives only in Phase 7, alongside a separate, unrelated on-device/edge-AI stretch item. See [`tech-stack.md`](./tech-stack.md#mobile--distribution) for the full reasoning.

## Phase 0 — Foundations — ✅ complete (local-first; see note below on the deferred AWS deploy)
**Goal:** empty-but-real skeleton, deployed.

**What shipped:**
- Repo structure: `Frontend/`, `Backend/`, `Docs/` (this doc set)
- FastAPI app with health check, Postgres connection, Alembic migrations set up
- React app scaffolded (Vite + TS + Tailwind + shadcn/ui), talking to the health check endpoint via TanStack Query
- PWA basics wired in (`vite-plugin-pwa`: web app manifest + service worker) — this is the only mobile-distribution mechanism planned; see [`tech-stack.md`](./tech-stack.md#mobile--distribution) for why a native/Capacitor wrapper is an optional stretch item, not a Phase 0 commitment
- Docker Compose for local dev (Postgres w/ pgvector, Valkey, API, frontend)
- GitHub Actions: lint + typecheck + basic pytest/Vitest running on PR

**Deliberately not done, and why:**
- **An early AWS staging deploy (ECS/Fargate or App Runner)** — a specific, explicit call made at the very start of this project (not a slip): every phase since has been built and verified against Docker Compose locally, with the entire seven-phase feature set (RAG, GraphRAG/Neo4j, background jobs, MCP server, eval suite, ML model) landing and being demoed against that local stack. Standing up real AWS infra (networking, ECS task defs/IAM, RDS, secrets management) before there was a real product to deploy would have been infrastructure work ahead of a real requirement — the same "don't build ahead of an actual need" principle Phase 1 applies to auth. A real AWS deploy remains the natural next step once this feature set needs to be reachable outside a local machine (e.g. for sharing a live demo link), and every architectural choice made along the way (Docker images per service, `DATABASE_URL`/env-var-driven config, stateless API containers) was made specifically so that move is a deploy-config exercise, not a rewrite.

## Phase 1 — Pokédex, Team Builder, and Calculator, no AI yet — ✅ complete
**Goal:** Master Ball's competitive tools — Pokédex, team import, and deterministic analysis — work, fully tested, before any LLM is involved. This is the foundation everything else (including the AI layer) is built on, not a placeholder to get past quickly.

**What shipped:**
- Pokédex data model (`species`/`moves`/`abilities`/`natures`/`type_matchups`/`items`), seeded from `poke-env`'s Showdown-sourced Gen 9 data via a re-runnable `scripts/seed_pokedex.py` — see [`backend/README.md`](./backend/README.md#data-seeding) and [`tech-stack.md`](./tech-stack.md#backend) for why `poke-env`
- `get_pokemon_profile` tool + standalone Pokédex UI (browse/search/filter + detail page) — base stats, full gen-9-legal movepool, abilities, computed type matchups, natures reference, a *full* evolution chain (every stage of the line, root to tip, with real per-stage trigger conditions — not just a Pokemon's immediate neighbors), and Mega Evolution formes shown inline with their own full profile (stats/movepool/abilities recomputed, not just a stat delta). Ability/move descriptions are real, complete text fetched from PokeAPI at seed time (~98% coverage), not a hand-typed subset — see [`backend/README.md`](./backend/README.md#ability-move-descriptions-real-data-only-never-a-hardcoded-stopgap).
- Cross-linked reference pages: every move, ability, and type shown anywhere in the app links to its own detail page (`get_move_detail`/`get_ability_detail`/`get_type_detail`) showing the matching Pokémon (`Species.learnable_moves`'s GIN index backs the move lookup). Items (Life Orb, Choice items, Arceus plates, Mega Stones, resist berries, etc. — 265 battle-relevant held items, PokeAPI's *only*-source-in-this-app data since `poke-env` has none) get their own detail pages too, reachable by direct link/URL for now — see [`backend/README.md`](./backend/README.md#items-pokeapi-is-the-only-source-not-just-the-description-text).
- `calculate_damage` tool — a from-scratch Gen 9 formula implementation (not a wrapper around an existing calc library), covering stat calc/stages, STAB (incl. Adaptability/Terastallization), the full type chart, weather, screens, crits, burn/Guts, and a curated set of common items/abilities — every test hand-derives its expected value in a comment; see [`backend/damage-calc.md`](./backend/damage-calc.md) for the full scope statement and what's explicitly deferred. `pytest-benchmark` holds it at ~15ms mean, well inside the sub-100ms target.
- Showdown team-import parser (via `poke-env`'s `Teambuilder`, not hand-rolled regex) and `analyze_team` tool — type coverage, speed tiers, a full weakness matrix, and simple heuristic role-compression flags (shared-weakness detection, missing-strong-attacker checks)
- Frontend: Pokédex browser + detail, move/ability/type/item detail pages, Calculator, and Team Builder (paste-import + manual slot editor) pages, wired with React Router (new dependency this phase). Team Builder state lives in the browser (Zustand + `localStorage`), not a server-side table — see the scope note below.
- SEO, applied everywhere and made a standing per-page convention going forward (not just a Phase 1 pass): a `Seo` component (React 19's native `<title>`/`<meta>`/`<link>` hoisting, no `react-helmet`) on every page, `Breadcrumbs` (visible nav + matching `BreadcrumbList` JSON-LD) on every detail page, a `noindex` 404 catch-all route, `robots.txt`, and a DB-driven `generate_sitemap.py` script — see [`frontend/README.md`](./frontend/README.md#seo) and [`README.md`](./README.md#seo-every-page-is-a-real-indexable-shareable-page).
- Modern, theme-aware scrollbar styling (thin, rounded, `--scrollbar-thumb`/`--scrollbar-thumb-hover` tokens) across both Firefox and WebKit engines — see [`frontend/README.md`](./frontend/README.md#theming--design-system).
- Global header search — one autofill-as-you-type box (`GET /search`, ranked/grouped server-side) finding Pokemon, moves, abilities, items, and types and jumping straight to the matching detail page — see [`frontend/README.md`](./frontend/README.md#global-search) and [`backend/README.md`](./backend/README.md#global-search).
- Per-stat min/max ranges (level 100, 0/31 IVs, 0/252 EVs, hindering/beneficial nature) shown alongside every base stat bar, computed once server-side and shared with the Damage Calculator's own stat formula — see [`backend/README.md`](./backend/README.md#minmax-stat-ranges) and [`frontend/README.md`](./frontend/README.md#minmax-stat-ranges-statbars).
- Pokedex browser reorganized into generation tabs (All / Gen 1-9, National Dex number ranges) that combine with the existing search/type filters — see [`frontend/README.md`](./frontend/README.md#pokedex-generation-tabs) and [`backend/README.md`](./backend/README.md#generation-filter-pokedex-browser-tabs).

**Deliberately not done, and why:**
- **Auth / server-side team persistence** — descoped after discussion: nothing in Phase 1 actually needs to know *who* the user is (`analyze_team` takes a team payload directly, not a `team_id`), so building accounts now would be infrastructure ahead of a real requirement. Real accounts land in Phase 3, when session/battle-result logging is inherently tied to a specific person.
- **Standalone browse/list pages for moves/abilities/types/items, and a real item picker for the Calculator/Team Builder's item field** — descoped after discussion: detail pages are reachable by clicking through from a Pokémon (or by direct URL for items), which covers the actual cross-linking need; a dedicated `/items` index or replacing the free-text item input is a natural follow-up, not required for Phase 1's scope.
- Everything listed in [`backend/damage-calc.md`](./backend/damage-calc.md)'s "explicitly deferred" section (the long tail of ability/item interactions, full VGC doubles targeting, variable-base-power moves beyond a curated set, Stellar Tera type).
- Tournament usage % — needs Phase 5's data pipeline.

## Phase 2 — Conversational Team Doctor (RAG + first agent) — ✅ complete
**Goal:** the flagship "ask anything, reasoned and grounded" experience works — this is the actual differentiator, not a generic RAG demo.

**What shipped:**
- Knowledge base slice: 12 original, hand-written strategy documents (10 top-OU Pokemon + 2 general mechanic/archetype notes) — **not scraped Smogon prose**, since Smogon's analyses are copyrighted editorial content, not an open data feed the way PokeAPI is; see `Backend/app/data/knowledge_base/README.md` for the full reasoning. `scripts/ingest_knowledge_base.py` chunks them with LlamaIndex's `SentenceSplitter` and embeds with a local `fastembed` model (no API key needed) into pgvector (HNSW cosine index) — idempotent, re-runnable.
- `retrieve_context` tool (`app/tools/retrieval.py`) — real pgvector cosine search with citations (source id, title, url), tag filtering, tested against the real ingested knowledge base.
- First LangGraph agent (`app/agent/graph.py`): router → tool_calls → synthesizer → direct_reply, with `get_pokemon_profile`/`calculate_damage`/`retrieve_context` bound as tools. Router uses OpenAI, synthesizer uses Claude via Anthropic's API directly (Bedrock deferred until real AWS credentials are wired up — see `backend/README.md`'s "AI agent (Phase 2)" section for why that's a config-level swap, not a rewrite) — no hardcoded stopgap if a provider key is missing, `/chat` returns a clear 503 instead.
- `POST /chat` + `WS /chat/ws` (token-streaming for the synthesizer step) — see `backend/README.md`.
- LangSmith tracing config wired (`configure_langsmith()`, opt-in via env vars) from day one of the agent existing.
- Tested via a fake-chat-model test double for real graph-wiring/branching coverage without needing a paid API key, plus real-data coverage for `retrieve_context` itself.
- Frontend chat widget (`/professor`) — streams the synthesizer's tokens live over `WS /chat/ws`, renders RAG citations as badges under each answer, and shows a missing-API-key 503 as a normal (if visually distinct) chat bubble rather than crashing — see [`frontend/README.md`](./frontend/README.md#conversational-team-doctor-phase-2-ui).

**Deliberately not done, and why:**
- `analyze_team` isn't bound as an agent tool yet — it needs a full 6-Pokemon team payload that isn't reliably extractable from free chat text without more scaffolding (structured-output-parsing a pasted Showdown export first); the existing `POST /team/analyze` REST endpoint already covers that flow directly.
- Durable server-side conversation sessions (persist threads across devices/accounts) — the client already sends recent prior turns as `history` per request so follow-ups work in-session; account-backed thread storage is still a natural follow-up.
- Exercising the full graph against a real provider end-to-end is a manual, opt-in check (real API keys cost real money) rather than something CI runs on every PR — RAGAS/promptfoo-gated CI is Phase 4's job.

## Phase 3 — Mental-Game Coach — ✅ complete
**Goal:** the second flagship feature — the one genuinely zero-competitor gap found in research. Turns Master Ball from "a tool that answers questions" into "a coach that pays attention to how you're doing."

**What shipped:**
- Session/battle-result tracking: `BattleLogEntry`/`PushSubscription` tables, scoped to an anonymous client-generated `client_id` (no accounts yet — nothing here needs to know *who* someone is) — see [`backend/README.md`](./backend/README.md#mental-game-coach-phase-3).
- Loss-streak detection implementing the community's own "two-loss rule": `check_tilt_risk` (`app/tools/battle_log.py`) is a plain deterministic loop over recent results, no LLM involved — a win anywhere resets the streak, `TILT_STREAK_THRESHOLD = 2` triggers the nudge.
- Push notifications via the browser's Web Push API — VAPID keys (`scripts/generate_vapid_keys.py`), `pywebpush` server-side, delivered through a real custom service worker (`Frontend/src/sw.ts`, switching `vite-plugin-pwa` to the `injectManifest` strategy specifically to get a `push`-event hook) — no native app or third-party push SDK. Gracefully absent (not broken) when VAPID keys aren't configured, both server- and client-side.
- Post-loss explanation flow: `POST /sessions/post-loss-review` reuses the *exact same* Phase 2 LangGraph agent with a targeted prompt built from the logged loss's note, rather than a second LLM pipeline — see [`backend/README.md`](./backend/README.md#post-loss-explanation-flow--reuses-the-phase-2-agent-not-a-second-pipeline).
- Frontend: a check-in surface (`/professor/check-in`) — log a win/loss with a note, see the tilt nudge as an in-page banner in real time (independent of whether push permission was ever granted), manage the Web Push permission flow end-to-end (`usePushSubscription` hook), and request/read a post-loss review inline — see [`frontend/README.md`](./frontend/README.md#mental-game-coach-phase-3-ui--web-push).
- Tested: `test_battle_log.py` (tilt-detection logic against a real DB, no LLM/push involved) + `test_sessions.py` (HTTP layer, including the 503-when-unconfigured and 404-unknown-entry paths) backend-side; `CoachPage.test.tsx`/`MentalCoachPage.test.tsx` frontend-side (mocked network layer, real component/interaction behavior).

**Deliberately not done, and why:**
- Real user accounts — still not needed; the anonymous `client_id` model is deliberately carried forward from Phase 1's reasoning, not a shortcut specific to this phase.
- Automated Web Push delivery tests (real browser push requires a real subscribed endpoint) — `send_push_notification`'s success/failure paths are covered, but an actual end-to-end "does a notification appear" check is a manual smoke test, not CI-automatable without a headless-browser push mock.
- Mood/sentiment analysis of the free-text note — the tilt trigger is purely the deterministic loss-streak count; classifying *how* someone feels from their note text is exactly the kind of small on-device model Phase 7's edge-AI stretch item calls out, not pulled forward here.

## Phase 4 — Eval loop + MCP server — ✅ complete
**Goal:** close the quality loop, and ship a standalone MCP server as a real, independent artifact.

**What shipped:**
- Standalone MCP server (`Backend/app/mcp/`, built with the official Python SDK's `FastMCP`) exposing `get_pokemon_profile`, `calculate_damage`, and `analyze_team` — the *same* `app/tools/*` implementations the REST API and LangGraph agent already use, not reimplementations. `lookup_meta_stats` isn't exposed since it doesn't exist yet (Phase 5). Both `stdio` and Streamable HTTP transports are supported (`scripts/run_mcp_server.py`), the latter gated by a bearer-token `MCP_API_KEY` check. Manually verified against a real MCP `initialize` handshake over HTTP and documented for the official MCP Inspector; automated tests call `FastMCP.call_tool` directly in-process. Has its own README (`Backend/app/mcp/README.md`) — see [`backend/README.md`](./backend/README.md#mcp-server-phase-4) for the summary.
- Golden eval datasets (`Backend/eval/golden/*.jsonl`, checked into git, framework-neutral): 12 retrieval queries (one per knowledge-base doc), 4 chat regression questions, 2 prompt-injection red-team probes — see `Backend/eval/README.md`.
- Deterministic RAGAS retrieval eval (`scripts/run_ragas_eval.py`): runs the real `retrieve_context` tool against every golden query and scores it with exact source-id recall plus RAGAS's `NonLLMContextRecall`/`NonLLMContextPrecisionWithReference` (string-similarity metrics, no LLM judge, no API cost) — `reference_contexts` are loaded from the real knowledge-base files at eval time so it can't silently drift from what's actually ingested. Wired into the normal `pytest` run (`tests/test_ragas_eval.py`), not just a standalone script.
- LLM-judged chat eval (`scripts/run_llm_eval.py`): runs the real Phase 2 agent against the chat golden set and scores answers with RAGAS's `Faithfulness`/`ResponseRelevancy`, using this project's own synthesizer LLM as judge — deliberately manual/opt-in (real API cost per run), not part of the automated suite; fails clearly (non-zero exit, no fabricated score) when no provider key is configured, which *is* covered by an automated test.
- promptfoo suite (`Backend/eval/promptfoo/promptfooconfig.yaml`) hitting the real running `POST /chat` endpoint: the same 4 regression questions (keyword assertions) plus 2 prompt-injection red-team cases (`not-contains` assertions) — a live black-box check independent of the Python eval scripts, useful for before/after comparisons when changing prompts or swapping models.

**Deliberately not done, and why:**
- **CI-gating the promptfoo suite** — it needs a real running backend *plus* real provider API keys (a per-run cost), which is a separate, deliberate call from the RAGAS retrieval eval below. (The Postgres-in-CI gap this note originally flagged is now fixed — see Phase 5's note on `ci.yml`.)
- **Langfuse (self-hosted), for a first-hand LangSmith-vs-Langfuse comparison** — self-hosting means several new long-running Docker services (web/worker/ClickHouse/Redis/object storage), a meaningful infra addition rather than a quick add alongside the rest of this phase. Deferred, not abandoned — see `Backend/eval/README.md`.

## Phase 5 — Meta stats, Showdown replay coach, background jobs — ✅ complete
**Goal:** the harder, async, multi-step features, scoped to what's actually buildable today.

**What shipped:**
- Arq worker (`Backend/app/worker.py`), backed by the same Valkey instance Docker Compose already runs, deployed as its own `worker` Compose service (same image as `backend`, different command) — a daily cron job (`sync_usage_stats_job`), not a request thread ever calling out to Smogon live.
- Real meta/usage-stats pipeline: `UsageStats` table + `scripts/sync_usage_stats.py`, syncing from Smogon's own publicly-published Chaos stats dumps (`smogon.com/stats/YYYY-MM/chaos/FORMAT-CUTOFF.json` — the same real, freely-published aggregate data Smogon's own site and every third-party OU tool draws from, not scraped analysis prose). Normalizes weighted counts into percent shares, resolves teammate/checks-and-counters names to this app's own species ids where possible, and upserts idempotently (`ON CONFLICT DO UPDATE` on `(format, species_id)`) so re-running never duplicates rows. `lookup_meta_stats` tool + `GET /meta/{species_id}` + bound as an agent tool — verified end-to-end against the live Smogon endpoint (402 real Gen 9 OU Pokemon synced), not just a fixture.
- Showdown replay parser (`app/tools/replay_parser.py`) — a from-scratch implementation of (a practically-useful subset of) Showdown's own documented text protocol, not a wrapper around an existing library. Groups events by turn, renders a human-readable summary per event, and `fetch_replay` pulls the raw log from Showdown's own public, unauthenticated replay API. `POST /replay/parse`.
- Replay Coach: `build_replay_coach_prompt` turns a parsed replay into a prompt for the *exact same* Phase 2 agent graph (same "reuse the agent, don't stand up a second LLM pipeline" pattern as Phase 3's post-loss review) — `POST /replay/coach` returns a cited postmortem identifying the turning-point turns. Frontend: `/replay-coach` page (paste a replay URL/id or raw log, see the parsed turn list, request the AI postmortem).
- `scout_opponent` tool (`app/tools/scout.py`) composing `lookup_meta_stats` + `retrieve_context` into one combined report (real likely-set data + relevant strategy notes) — bound as an agent tool and its own `GET /scout/{species_id}` endpoint.
- First real use of Gemini as the multimodal specialist: `extract_team_from_image` (`app/tools/vision_import.py`, `langchain-google-genai`) transcribes a screenshotted team sheet into Showdown export text, which flows through the *exact same* `parse_showdown_team`/species-validation path a pasted-text import uses — `POST /team/import-image` + a frontend "Import from screenshot" button on the Team Builder. Gracefully returns a 503 (not a guessed team) when `GOOGLE_API_KEY` isn't configured, same pattern as the OpenAI/Anthropic/VAPID missing-key paths.
- Frontend: a real usage-stats panel (`UsageStatsCard`) on every synced Pokemon's detail page (rank/usage%/abilities/items/moves/Tera types/teammates/checks-and-counters, all real numbers) — renders nothing (not an error) for a Pokemon that hasn't been synced.
- Fixed the pre-existing `ci.yml` gap flagged at the end of Phase 4: the backend CI job now provisions a real `pgvector/pgvector:pg16` Postgres service, runs `alembic upgrade head` + `scripts.seed_pokedex` + `scripts.ingest_knowledge_base` before `pytest` — verified locally end-to-end against a throwaway, freshly-created container (no pre-existing state) before landing. This means the *entire* backend test suite (119 tests, including the RAGAS retrieval eval) now actually runs in CI, not just locally.
- `lookup_meta_stats`/`scout_opponent` also added to the Phase 4 MCP server (`app/mcp/server.py`), per its own "one implementation, three surfaces" principle — an MCP client gets the same real usage-stats/scouting tools the REST API and chat agent do.

**Deliberately not done, and why:**
- **Historical usage trends over time** — `usage_stats` keeps only the latest synced snapshot per `(format, species_id)` (upserted in place), not a time series; a trend chart is a natural follow-up (add a `synced_at`-keyed history table) but wasn't needed for the "what's this Pokemon actually running right now" use case this phase targets.
- **The Champions-specific video replay feature** — still correctly deferred to Phase 7's Premium item; this phase's Replay Coach is Showdown-log-based only, per the original scope note (Showdown has clean text logs today, Champions doesn't).
- **Automated live-network tests for `sync_usage_stats`/`fetch_replay`** — both are tested against realistic hand-built/fixture data (matching this project's fake-LLM/fixture-JSON testing pattern elsewhere), with the real live integrations verified manually once (see `Backend/tests/test_sync_usage_stats.py`'s docstring) rather than making the CI suite depend on smogon.com/Showdown's replay API being reachable and unchanged.
- **Real end-to-end testing of the Gemini vision import** — no `GOOGLE_API_KEY` is configured in this project's dev/CI environment (a real, recurring API cost, same call as Anthropic/OpenAI), so `extract_team_from_image` is verified via its 503-when-unconfigured path plus a mocked-transcription integration test, not a live Gemini call — same cost-discipline reasoning as Phase 4's LLM-judged eval being manual/opt-in.

## Phase 6 — AI-assisted Team Builder and GraphRAG (Neo4j) — ✅ complete
**Goal:** take the Team Builder (core since Phase 1 as a manual tool) the rest of the way to genuinely competitive with ChampTeams/ChampionsMeta, powered by a differentiated, harder-to-copy retrieval technique.

**What shipped:**
- Neo4j knowledge graph (`docker-compose.yml`'s `neo4j` service, Community edition) loaded by `scripts/load_graph.py` — built entirely from data this app already trusts (not a second data source): Phase 1's seeded Pokedex becomes `Pokemon`/`Type`/`Move`/`Ability`/`Item` nodes with `HAS_TYPE`/`CAN_LEARN`/`HAS_ABILITY`/`EVOLVES_INTO`/`EFFECTIVE_AGAINST` edges, and Phase 5's real synced Smogon usage stats (where available) become `PAIRS_WITH`/`COUNTERED_BY` edges. Idempotent (`MERGE` throughout) and verified end-to-end against real seeded data (1,484 Pokemon, 61k+ movepool edges) and, separately, against a completely fresh Postgres+Neo4j pair with no usage data synced (the exact shape CI runs in).
- `suggest_teammates` (`app/tools/graph_query.py`) — the actual GraphRAG query: traverses `HAS_TYPE`/`EFFECTIVE_AGAINST` to find the current team's real type weaknesses, then traverses again to find types that resist those weaknesses (mapped back to real Pokemon), and separately traverses real `PAIRS_WITH` usage-stats co-occurrence from the current team — merging both into one ranked candidate list where every reason is traced directly back to the specific graph edge that produced it, never a fabricated justification. This is deliberately a multi-hop graph question, not a single SQL join or a vector-similarity search — see `Docs/backend/README.md`'s "Knowledge graph (Phase 6)" section for the full case for GraphRAG here specifically.
- Three surfaces, one implementation (per `architecture.md`'s rule): `POST /team/suggest-teammates` (fast/free, called on every Team Builder edit), the `suggest_teammates` agent tool (LLM-reasoned prose on top of the same graph output, for "who should I add to my team" chat questions), and the MCP server's `suggest_teammates` tool (now 6 tools total) all call the exact same function.
- `app/graph/session.py`'s `GraphUnavailableError` — Neo4j is required local infra (not an optional API key), so an unreachable graph surfaces as a clean 503/ToolError at all three surfaces, same shape as a missing-provider-key error but for infra instead of config.
- Frontend: `TeamSuggestionsPanel` on the Team Builder page — live, graph-derived teammate suggestions (with real usage-stats/type-resist reasons) as the team changes, linking each candidate to its own Pokedex page.
- Also fixed, alongside this phase: `ci.yml`'s backend job now also provisions a real Neo4j service and runs `scripts/load_graph.py` before `pytest` — every graph-touching test (`test_graph_query.py`'s synthetic-graph-fixture tests, `test_load_graph.py`'s real-data idempotency test, `test_mcp_server.py`'s `suggest_teammates` test) runs in CI now, not just locally. Verified against completely fresh (no pre-existing state) Postgres+Neo4j containers before landing.

**Deliberately not done, and why:**
- **A combined multi-type-stacking weakness computation in the graph** — `_team_weaknesses` counts, per type, how many team members it's super-effective against *per individual type* (not the fully-multiplied dual-type product `app/tools/team_analysis.py`'s Postgres-based `analyze_team` already computes precisely). This is intentional: the graph tool only needs "is this roughly a real weakness worth resisting," not a second, independently-maintained precise weakness formula that could quietly disagree with the Team Builder's own analysis.
- **Historical/format-agnostic graph data** — `PAIRS_WITH`/`COUNTERED_BY` edges are scoped to a single format (`gen9ou` by default, via a relationship property) sourced from whatever `UsageStats` happens to be synced; multi-format graph support is a natural follow-up (parameterize `load_graph`'s `--format` and the query layer together) once there's a real need to compare formats side-by-side.
- **LLM reasoning wired into the REST endpoint itself** — `POST /team/suggest-teammates` deliberately returns the raw graph-derived data (fast, free, no API cost), not an LLM-narrated version of it; that's what the `suggest_teammates` agent tool is for when a user actually asks in chat. Baking an LLM call into the fast structured endpoint would slow down and add cost to something meant to update live as the team changes.

## Phase 7 — Premium features and stretch goals
**Goal:** the features that were deliberately deferred, plus polish work that only makes sense once there's real feature depth to show for it. Everything in this phase is genuinely optional and unordered relative to each other — pick based on time available and product value.

1. **AI Battle Postmortem for Pokémon Champions (Premium)** — the single most differentiated idea from the research, and the most expensive: user uploads a screen recording they already made of a Champions match (no live capture, no in-app recording — that's explicitly out of scope); Gemini's multimodal/video understanding reconstructs the turn-by-turn battle; the agent coaches the postmortem the same way the Showdown-log-based Replay Coach does in Phase 5. Gated as Premium specifically because the compute cost (video-understanding API calls) is real and per-use, unlike the mostly-cached/batched core product. **Not built** — correctly deferred, per its own scope note above: it's genuinely the most expensive item here (real, recurring video-understanding API cost, and no way to test it without one), unlike the other items in this phase which were buildable with zero ongoing per-use cost.
2. **On-device/edge AI (WebGPU + Transformers.js/WebLLM) — ✅ shipped.** A small local model running entirely client-side for an instant mood/tilt signal — see [`tech-stack.md`](./tech-stack.md#on-deviceedge-ai-optional-stretch--see-roadmapmd). Entirely browser-based; doesn't depend on item 3 below at all. Concretely: an instant mood/tilt signal on the Mental-Game Coach's post-loss note — `Frontend/src/workers/moodWorker.ts` runs `@huggingface/transformers` (Transformers.js) in a dedicated Web Worker, classifying the note with a small quantized sentiment model (WebGPU-accelerated where available, WASM fallback otherwise) entirely in-browser, with zero network round-trip after the model's one-time download. See [`frontend/README.md`](./frontend/README.md#on-device-mood-model-phase-7) for the full design note (debouncing, stale-response handling, PWA-precache exclusion, and why it's mocked rather than run for real in the Vitest suite).
3. **Native app packaging (Capacitor) + Google Play submission — optional, unscheduled** — demoted from a planned deliverable to a true "only if there's spare time and it still sounds fun" stretch item. See [`tech-stack.md`](./tech-stack.md#mobile--distribution) for the full reasoning: it adds real recurring store-maintenance overhead unrelated to the AI work, and 2026 research turned up two independent reasons to be cautious about it specifically for this app (Google Play's policy tightening around "AI companion apps," and PWAs now out-converting Play Store listings on install rate anyway). **Not built** — the reasoning above still holds, so it stayed unscheduled.
4. **Multi-cloud deploy** — same Docker containers redeployed to Google Cloud Run, model calls routed through Vertex AI. Not needed for the product; kept as a documented optional multi-cloud path even though AWS is primary here (see [`tech-stack.md`](./tech-stack.md#cloud-and-model-provider-decision-revisited) for why AWS is primary). **Not built** — genuinely optional; AWS remains this project's actually-deployed target.
5. **XGBoost win-probability model — ✅ shipped.** Tabular model over structured team-composition features, served alongside the LLM-based analysis. See [`backend/README.md`](./backend/README.md#win-probability-model-phase-7) for the full design note — the short version: `app/ml/features.py` computes real per-team feature vectors (avg stats, type diversity, type-matchup coverage) from the real seeded Pokedex; `app/ml/simulate.py` documents, up front, that training *labels* come from a synthetic battle-outcome simulator, since no dataset of real logged ladder-match results exists for this project; `scripts/train_win_probability_model.py` trains an `XGBClassifier` (AUC ~0.71 on held-out synthetic data — real signal recovered from labeled outcomes, not a claim about real human matches) and saves it to a committed `app/data/ml/win_probability_model.json`. Same "one implementation, three surfaces" shape as every other tool here: `POST /ml/win-probability`, the `predict_win_probability` agent tool, and the MCP server's `predict_win_probability` tool (now 7 tools total) all call the same function. Frontend: `WinProbabilityPanel` on the Team Builder page (paste an opponent team, get an estimate — the caveat string is always shown alongside the number, never a bare percentage). Every surface's tests train their own throwaway model against a temp path rather than depending on the real committed artifact, and `ci.yml` runs the real training script once more as an end-to-end smoke test.
6. **Multi-server MCP composition** — the Master Ball MCP server plus a second public MCP server (e.g., fetch/filesystem) used together from one client, with documented notes on capability-conflict handling. **Not built** — genuinely optional; the existing MCP server (Phase 4) already covers the core authoring work (transport/auth/typed schemas), and composing a second public server is additive polish rather than new ground.
7. **Kubernetes (EKS)** — only if a concrete limitation of ECS/Fargate is actually hit. **Not built** — no such limitation was hit; ECS/Fargate has handled this project's actual deploy needs, which is itself a defensible reason not to reach for k8s prematurely.
8. **Playwright E2E suite — ✅ shipped.** Covers the full "import team → get analysis → ask a follow-up in chat → get a cited answer" flow, plus the Phase 6/7 additions (teammate suggestions, win-probability estimate). See [`frontend/README.md`](./frontend/README.md#end-to-end-tests-playwright-phase-7) for the full scope and how it's kept independent of real LLM provider keys.
